# Когда Ozon не отвечает: VPN, маршруты, прокси

## Как отличить эту проблему от других

Запустите `ozon_api_selftest` или `--check`. Смотрите на форму отказа:

| Что видно | Что это значит |
|---|---|
| `HTTP 401` / `HTTP 403` | Ozon вас услышал и отказал. Проблема в ключе |
| `HTTP 404` | Ozon отключил эту версию метода |
| `HTTP 400` | Ozon услышал и не принял запрос |
| **`СЕТЬ timeout`** | **Запрос до Ozon не дошёл. Проблема в маршруте** |
| `СЕТЬ dns` | Имя не разрешается — под VPN DNS часто подменяется |
| `СЕТЬ refused` | Соединение активно отклонено — обычно неверный адрес прокси |

Различие принципиальное. Таймаут означает, что Ozon вообще не участвовал в разговоре: пакеты ушли и не вернулись. Искать причину в ключах, коде или версиях методов бесполезно — там всё в порядке.

Если **ни один** метод не ответил и все сбои сетевые, `ozon_api_selftest` скажет об этом прямо и покажет варианты — разбирать методы по одному в такой ситуации бессмысленно.

## Откуда берётся конфликт

Claude на машине работает через VPN. Ozon Seller API из-под этого VPN недоступен: запросы уходят в туннель и не возвращаются. Обе программы нужны одновременно, а сетевые требования у них противоположные.

Ключ к решению: **это конфликт маршрутов, а не программ**. Значит, чинится он тоже на уровне маршрутов, и вариантов ровно три.

## Вариант 1 — сервер на VPS в России (рекомендуется)

Самый чистый: проблема не обходится, а исчезает.

```
Ваш ноутбук           серверы Anthropic            VPS в России
   (под VPN)  ──────►  claude.ai / приложение  ──►  ozon-seller-mcp  ──►  Ozon
```

Запрос к Ozon уходит с VPS, где никакого VPN нет. Ваша машина в этой цепочке вообще не участвует — она разговаривает только с Claude, а Claude ходит к серверу сам. VPN на ноутбуке становится безразличен.

Побочные выгоды, ради которых это стоит сделать даже без конфликта с VPN:

- сервер доступен со всех устройств, включая телефон;
- ключ Ozon лежит в одном месте, а не копируется на каждую машину;
- сервер работает, когда ноутбук закрыт.

Настройка — [`docs/REMOTE.md`](REMOTE.md).

**Что проверить:** VPS должен быть доступен из интернета с адресов Anthropic — запрос идёт от них, а не от вас. Российский хостинг обычно доступен снаружи, но убедитесь, что провайдер не закрывает входящие соединения из-за рубежа.

## Вариант 2 — исключить Ozon из VPN (split tunneling)

Быстро и без сервера, если ваш VPN-клиент это умеет.

**По приложению.** Многие клиенты позволяют исключить конкретную программу из туннеля. Исключите бинарник `ozon-seller-mcp` — тогда только его трафик пойдёт напрямую.

**По адресу.** Исключите `api-seller.ozon.ru` из туннеля. Учтите, что за именем стоят несколько адресов и они меняются, — исключение по имени надёжнее, чем по IP.

**Вручную через маршрут** (macOS, для проверки идеи):

```bash
dig +short api-seller.ozon.ru          # узнать адреса
route -n get default                    # шлюз физического интерфейса
sudo route add -host <IP> <шлюз>       # пустить в обход туннеля
```

Это разовая проверка: после переподключения VPN маршрут пропадёт, а адреса Ozon со временем сменятся. Годится, чтобы за минуту убедиться, что дело действительно в туннеле.

**Минусы:** настраивается на каждой машине заново, ломается при обновлении VPN-клиента, на телефоне неприменимо.

## Вариант 3 — прокси только для этого сервера

Середина: сервер остаётся у вас, но в Ozon ходит через российский узел. Остальная машина — под VPN как была.

```bash
OZON_PROXY=socks5://user:pass@vps.example.com:1080
```

Работает и в stdio, и в сетевом режиме. Настройка действует **только** на трафик к Ozon: другие программы её не видят, и наоборот — глобальный `HTTPS_PROXY`, выставленный для чего-то ещё, на этот сервер не влияет. Одна настройка — один эффект.

Прокси можно поднять на любом VPS одной командой:

```bash
ssh -D 1080 -N -f user@vps.example.com    # SOCKS5 через SSH, без установки софта
OZON_PROXY=socks5://127.0.0.1:1080 ozon-seller-mcp --check
```

Пароль в адресе не попадает в диагностику и логи — показывается только хост.

Если адрес прокси не разобрался, сервер **не запустится**. Молча пойти напрямую, когда вы просили через прокси, — худший исход: трафик уйдёт не туда, а вы будете уверены в обратном.

**Минусы:** ещё одно звено, которое может упасть; латентность выше; VPS всё равно нужен — а если он есть, вариант 1 обычно лучше.

## Что выбрать

| | Вариант 1 (VPS) | Вариант 2 (split tunneling) | Вариант 3 (прокси) |
|---|---|---|---|
| Нужен сервер | да | нет | да |
| Работает на телефоне | да | нет | нет |
| Настройка на каждой машине | нет | да | да |
| Переживает переподключение VPN | да | зависит от клиента | да |
| Времени на настройку | час | минуты | минуты |

Если VPS уже планируется под printpipe — берите вариант 1: он решает и этот конфликт, и задачу «работать со всех устройств», одной работой.

Если надо сегодня и на одной машине — вариант 2, а как только появится VPS, переезжайте на первый.

## Диагностика

`--check` показывает, с какого адреса вас видит внешний мир:

```
ozon-seller-mcp dev
Инструментов: 29
Режим stdio:  read-only
Прокси:       не задан (прямое соединение)
Внешний IP:   203.0.113.42

Проверяю ключи… не прошло
```

Запрос идёт через тот же транспорт, что и обращения к Ozon, — то есть через `OZON_PROXY`, если он задан. Поэтому показанный адрес это ровно тот, который увидит Ozon.

Если здесь адрес VPN-выхода, а Ozon отвечает таймаутом — причина найдена, дальше можно не искать.

## Почему сетевые сбои не повторяются

Клиент повторяет запросы при `429` и `5xx`, но **не** при сбое соединения. Маршрут за секунду не чинится: повторы превратили бы один таймаут в четыре и на минуту отложили бы момент, когда вы увидите причину.
