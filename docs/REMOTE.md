# Сетевой режим: один сервер на все устройства

Тот же бинарник умеет работать двумя способами:

- **stdio** — Claude запускает сервер подпроцессом на вашей машине. Просто, но работает только там, где стоит бинарник.
- **Streamable HTTP** — сервер живёт на VPS, к нему подключаются ноутбук, рабочая машина и телефон. Ключ Ozon при этом лежит в одном месте, а не копируется на каждое устройство.

## Что меняется, когда сервер выходит в сеть

Пока сервер работал по stdio, защита была неявной, но надёжной: добраться до него мог только процесс, который его породил. Никакой пароль был не нужен.

Как только тот же сервер доступен из интернета, эта защита исчезает целиком. Любой, кто знает адрес, может менять цены в вашем магазине. Поэтому:

- сервер **не запускается** в сетевом режиме без токенов;
- токенов **два**: читающий и пишущий;
- режим определяется **токеном запроса**, а не настройкой процесса.

Последнее — главное. Устройство с читающим токеном физически не может выполнить запись: проверка стоит не в настройках сервера, а в обработке каждого запроса, и никакая формулировка в чате её не обойдёт. На телефон ставите читающий токен, пишущий держите только там, где действительно правите магазин.

Если пишущий токен не задавать вообще, изменить магазин через сеть будет нельзя ничем.

## Ограничение, которое решает всё остальное

Чтобы сервер работал в мобильном приложении и в вебе, **он должен быть доступен из публичного интернета**: запрос идёт с серверов Anthropic, а не с вашего устройства. VPN, Tailscale и «спрятать за домашним роутером» не подойдут — Claude туда не попадёт.

Отсюда и требования: TLS обязателен, токен обязателен, порт приложения наружу не смотрит.

## Развёртывание на VPS

### 1. Сборка и установка

```bash
git clone https://github.com/MainAlexStark/ozon-seller-mcp
cd ozon-seller-mcp
go build -ldflags "-s -w -X main.version=$(git describe --tags --always)" \
  -o /usr/local/bin/ozon-seller-mcp ./cmd/ozon-seller-mcp
```

### 2. Токены

```bash
ozon-seller-mcp --gen-token   # читающий
ozon-seller-mcp --gen-token   # пишущий
```

Генерируйте **разные**. Один и тот же токен в обоих полях сводит на нет весь смысл разделения.

### 3. Конфигурация

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin ozonmcp
sudo cp deploy/ozon-seller-mcp.env /etc/ozon-seller-mcp.env
sudo chmod 600 /etc/ozon-seller-mcp.env
sudo nano /etc/ozon-seller-mcp.env      # ключ Ozon и токены
```

Секреты лежат в файле, а не в строке запуска: аргументы процесса видны любому пользователю через `ps`.

### 4. Служба

```bash
sudo cp deploy/ozon-seller-mcp.service /etc/systemd/system/
sudo systemctl enable --now ozon-seller-mcp
sudo systemctl status ozon-seller-mcp
```

Юнит слушает `127.0.0.1:8571` — наружу порт не выставлен.

### 5. TLS через Caddy

```bash
sudo cp deploy/Caddyfile /etc/caddy/Caddyfile
sudo nano /etc/caddy/Caddyfile          # заменить домен
sudo systemctl reload caddy
```

Сертификат Caddy выпустит и будет продлевать сам.

В конфиге пути **не логируются**. Это не мелочь: токен приходит в адресе, и обычный access-log сложил бы ваши секреты в файл, который потом уедет в бэкап.

### 6. Проверка

```bash
curl https://ozon-mcp.example.com/healthz
# {"status":"ok"}

curl -s https://ozon-mcp.example.com/mcp \
  -H "Authorization: Bearer <читающий токен>" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | head -c 300
```

Без токена должен приходить `401`.

## Подключение устройств

### Телефон и claude.ai

Настройки → Connectors → Add custom connector, адрес:

```
https://ozon-mcp.example.com/mcp/<токен>
```

Токен в адресе — потому что в этом интерфейсе есть только поле URL, задать свой заголовок негде. На телефон ставьте **читающий** токен.

### Claude Code

```bash
claude mcp add --transport http ozon \
  https://ozon-mcp.example.com/mcp \
  --header "Authorization: Bearer <пишущий токен>"
```

Здесь заголовок доступен, поэтому секрет не попадает в адрес.

### Claude Desktop

Через тот же интерфейс Connectors, что и на claude.ai — адрес с токеном в пути.

## Про секрет в адресе

Это осознанный компромисс, а не недосмотр. Плата за то, что решение работает на телефоне:

- адрес может осесть в логах прокси (поэтому логирование путей выключено), в истории браузера и в конфигурации клиента;
- отозвать доступ можно только сменой токена — раздельного отзыва по устройствам нет;
- утёкший читающий токен показывает чужому человеку ваш каталог, цены и обороты.

Чем это компенсируется: токен длинный и случайный, меняется одной строкой в `/etc/ozon-seller-mcp.env` плюс перезапуск, а пишущий токен живёт только на устройствах, где вы действительно правите магазин.

Спецификация MCP предлагает вместо этого OAuth 2.1 — с короткоживущими токенами и настоящим отзывом доступа. Если сервером будет пользоваться кто-то кроме вас, переходить надо туда.

## Ротация токенов

```bash
sudo nano /etc/ozon-seller-mcp.env      # новые значения
sudo systemctl restart ozon-seller-mcp
```

Старые токены перестают работать сразу. Не забудьте обновить адрес в подключённых клиентах.

Меняйте токены, если адрес попал в переписку, в скриншот или в чужие руки. Это дёшево — делайте не задумываясь.

## Docker

```bash
docker build -t ozon-seller-mcp .
docker run -d --name ozon-mcp \
  -p 127.0.0.1:8571:8571 \
  --env-file /etc/ozon-seller-mcp.env \
  ozon-seller-mcp
```

Публикация порта тоже только на петлю: TLS остаётся за обратным прокси.

## Что ещё стоит включить

**Ограничение по адресам.** Запросы приходят с серверов Anthropic. Если вы не пользуетесь сервером через `curl`, можно пустить на `/mcp` только их диапазоны — тогда утёкший токен станет бесполезен для постороннего. Диапазоны публикует Anthropic; при их изменении подключение отвалится, поэтому взвесьте.

**Мониторинг отказов.** В журнале видны строки «отказ в доступе» с адресом источника. Всплеск таких строк означает, что адрес вашего сервера кто-то нашёл и перебирает токены.

```bash
journalctl -u ozon-seller-mcp -f | grep "отказ в доступе"
```

## Устройство транспорта

Сервер без состояния: `Mcp-Session-Id` не выдаётся и не требуется. Каждый запрос самодостаточен, поэтому переживает перезапуск процесса и не сломается за балансировщиком, если однажды понадобится второй экземпляр.

- `POST /mcp` — JSON-RPC внутрь, JSON наружу. Клиентам, принимающим только `text/event-stream`, ответ отдаётся одним SSE-событием.
- `GET /mcp` — `405`: сервер сам ничего не инициирует, поток server-to-client не нужен.
- `DELETE /mcp` — `204`: сессий нет, удалять нечего.
- Уведомления (сообщения без `id`) — `202` без тела.
- Заголовок `Origin` проверяется: сайт в браузере не должен ходить к серверу от вашего имени.

Оба транспорта — stdio и HTTP — используют одну реализацию протокола (`mcp.Server.HandleMessage`). Расхождение между ними означало бы разное поведение сервера в зависимости от способа подключения, а такое не отлаживается.
